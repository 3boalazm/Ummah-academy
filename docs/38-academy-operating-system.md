**شُحن 2026-10-17 (نظام تشغيل الأدمن):** واجهة واحدة ليست ووردبريس: مساحة العمل / مدير الموقع / تشغيل الأكاديمية / القبول / الفريق والحوكمة. النظرة العامة طوابير عمل. الموقع يبقى Astro+سفيلتيا (مسودة→معاينة→اعتماد→نشر). القبول Lead→تجربة محجوزة→مكتملة→مدفوع من سجلات البوابة. التقرير للأسرة بعد اعتماد الأدمن/التشغيل. ## العربية

### 0. اللي موجود أصلًا (متبدأش من صفر)

البوابة الحالية (`npm run portal`) مش سكتش. فيها كيانات مفصولة واختبارات تمنع إن الرقم يبقى خانة محفوظة:

| الطبقة | الحالة |
|---|---|
| أدوار: أدمن / تشغيل / معلم / ولي / طالب | مفروضة على السيرفر |
| طالب ≠ مستخدم ≠ ولي ≠ معلم | موجود |
| اشتراك ≠ كورس ≠ تسجيل ≠ دورة دفع | موجود |
| حصة ≠ حضور ≠ تقرير | موجود |
| رصيد يُشتق ولا يُخزَّن كعداد | موجود |
| منهج / تحديد مستوى / واجب / تقييم | عقد أكاديمي في `academic.mjs` — الواجهة لسه ناقصة |
| تدقيق append-only | موجود للأدمن والتشغيل |
| تخزين | ملف JSON تجريبي. **ليس إنتاج أطفال** |

الموقع Astro يظل الواجهة العامة. الدخول الحقيقي على `portal.ummahacademy.net` بعد بوابات الإطلاق.

### 1. الشكل اللي أنصح به

```
[ الموقع التسويقي · Astro ]
        │ تجربة / حجز
        ▼
[ API واحد · نفس الدومين الحالي في portal/src ]
        │
        ├── /app/owner     لوحة المالك والتشغيل والمالية
        ├── /app/teacher   يوم المعلم: حصص، حضور، تقرير، واجب
        └── /app/family    ولي الأمر والطالب (صلاحيات أضيق)
```

فرونت **ويب عادي** (متصفح، موبايل، يتثبّت PWA لاحقًا). مش تطبيقين ستور.  
باك **سيرفر واحد** يرفض الأمر لو السياسة تمنعه — إخفاء الزر ليس حماية.

ثلاث واجهات، نفس الـ API، نفس قاعدة البيانات. اختلاف الشاشة حسب الدور، مش حسب قاعدة بيانات.

### 2. سير العمل الأكاديمي (من التسجيل للحصة للتقييم)

هذا هو العمود الفقري. كل خطوة حالة، وليست فورم:

```
ليد / تجربة
  → تحديد مستوى (rubric + محاولة مؤرخة)
    → تسجيل في منهج/مستوى (Enrollment)
      → إسناد معلم (Assignment بتاريخ بداية/نهاية)
        → سلسلة حصص (Session بالـ UTC)
          → حضور (حاضر / غياب طالب / غياب معلم / إلغاء)
            → تقرير الحصة (إجباري بعد الإتمام)
              → واجب + تسليم + تصحيح
                → حدث تقدّم مربوط بمصدر (مش شريط وهمي)
                  → مراجعة مستوى / نقلة منهج
```

قواعد لا نكسرها (موجودة في `policy.mjs` وينبغي أن تبقى في قاعدة البيانات):

- الحصة المجدولة لا تُخصم. المكتملة تُخصم مرة.
- إلغاء الأسرة قبل ٢٤ ساعة لا يُخصم. بعدها يُخصم. إلغاء المعلم/الأكاديمية لا يُخصم.
- غياب الطالب يُخصم. غياب المعلم لا.
- تغيير المعلم لا يعيد كتابة الحصص الماضية.
- التقدّم الدراسي ≠ الحضور ≠ دفع الاشتراك. ثلاثة حقول.

ما يلزم بناؤه في الواجهة فوق العقد الأكاديمي:

1. بنك منهج لكل مسار (تجويد / عربي / أشبال / إسلاميات) بإصدارات.
2. شاشة تحديد مستوى للمعلم، واعتماد نقلة المستوى للأدمن.
3. دفتر الحصة: حضور في ٣٠ ثانية، ثم تقرير إجباري قبل إغلاق اليوم.
4. واجب مربوط بهدف الدرس، تسليم الطالب أو الولي، تصحيح المعلم.
5. ملف الطالب 360 كما هو، مع محور أكاديمي حي (مش «قريبًا»).

### 3. سير العمل البيزنس (من الليد للفلوس للمتابعة)

```
زيارة الموقع
  → ليد (مصدر + UTM + موافقة)
    → تجربتان مجانيتان (من غير خصم بطاقة)
      → نتيجة التجربة: تحويل / لا يناسب / يحتاج متابعة
        → اشتراك + دورة + دفعة
          → فاتورة دفترية (ضريبية لاحقًا بعد قرار قانوني)
            → تجديد / تجميد / إلغاء
              → متابعة بمالك وموعد ونتيجة
                → صندوق واتساب: مسودة → محاولة → دليل وصول
```

المالك يشوف هذا العمود كأرقام يومية، لا كجداول خام:

- تجارب هذا الأسبوع → محوَّلة كم؟
- حصص اليوم: مكتملة بلا تقرير (طابور أحمر)
- دفعات فاشلة لم تُسوَّ
- متابعات متأخرة بمالك
- معلمون بلا تغطية الغد
- أسر مجمَّدة ما زال عليها رصيد

### 4. ماذا يرى كل دور على الويب

**المالك / الأدمن**

- لوحة اليوم: تجارب، حضور، تقارير ناقصة، فلوس، مخاطر
- كل الطلاب والأسر والمعلمين
- اعتماد نقلة مستوى، تجميد، تجديد، إسناد معلم
- التدقيق: من غيّر ماذا، قبل وبعد
- التصدير CSV بلا أسرار
- الصحة: قيود مكسورة، بذور تجريبية في الإنتاج = رفض الإقلاع

**التشغيل (Ops)**  
نفس الرحلات اليومية بلا حذف قاعدة وبلا إعادة ضبط التجربة. تضييق صلاحيات التشغيل قرار مالك (`AUTH-010`) قبل الإنتاج.

**المعلم**

- جدول اليوم حسب منطقته
- دخول الغرفة (لما يتوصل مزوّد الاجتماع)
- حضور → تقرير → واجب في مسار واحد
- طلابه فقط. لا فواتير. لا أبناء أسرة غير مسندين

**ولي الأمر**

- أبناؤه المصرَّح بهم فقط
- الحصة القادمة، التقرير بعد الحصة، الواجب
- الفاتورة إن `canViewBilling`
- التسجيل إن `canViewRecordings`
- طلب إعادة جدولة، لا تعديل صامت للجدول

**الطالب (إن سُمح عمرًا)**  
نفسه فقط: حصصه، واجبه، تقريره المنشور. الدخول يمكن أن يبقى مغلقًا للأطفال الصغار (يوسف في البذرة نموذجي).

### 5. الباك — كيف يتكمل من غير إعادة كتابة

| الآن | الإنتاج |
|---|---|
| `portal/src/domain/*` منطق | يبقى مصدر الحقيقة. لا يُنقل للمنصة الجديدة |
| ملف JSON | Postgres (أو ما يعادله) + migrations. `DATA-002` |
| جلسة كوكي | نفس الكوكي + `Secure` + إلغاء من السيرفر |
| واتساب يدوي | مزوّد يكتب نتيجة الإرسال في سجل المحاولة |
| غرفة الحصة «غير موصولة» | Daily / Whereby / Google Meet بروابط قصيرة العمر |
| دفع دفتر يدوي | Stripe (أو تحويل) على `recordPayment` بمفتاح عدم تكرار |
| رفع 1MB محلي | تخزين كائنات + سكان + رمز 15 دقيقة كما هو |

قاعدة ذهبية: **الأمر يدخل من الـ API، والسياسة في الدومين، والقاعدة تفرض القيود.** الواجهة لا تخترع حالة.

وظائف الخلفية (workers)، ليست طلب HTTP:

- تذكير واتساب قبل الحصة بـ ١٥ دقيقة
- طابور «تقرير ناقص» بعد منتصف ليل منطقة المعلم
- إعادة محاولة دفع فاشلة
- انتهاء رمز التسجيل
- نسخة احتياطية ليلية + تمرين استعادة (`DATA-005`)

### 6. ما لا أنصح به

- Moodle / Canvas / Teachable / MemberPress تاني — هترجعوا لطبقة فوق وردبريس.
- تطبيقين iOS/Android قبل ما الويب يستقر. PWA بعد الحضور والتقرير يشتغلوا على الموبايل.
- شات حي داخل البوابة. واتساب هو القناة، والصندوق يسجّل المحاولة.
- لوحة واحدة لكل الأدوار. المعلم مش هيستخدم شاشة المالك.
- خلط Astro بالبوابة. `BASE-001` يبقى: موقع عام ثابت، تشغيل مصادق.

### 7. ترتيب البناء (بعد قرارات المالك)

1. **أسبوع الدومين الحي:** Postgres + نقل عقد `store`/`academic`/`policy` كما هي + رفض الإقلاع من غير سر.
2. **يوم المعلم:** حضور + تقرير إجباري + طابور التقارير الناقصة. هذا يحرّك الأكاديمية أكثر من أي شاشة أخرى.
3. **تحديد المستوى → تسجيل المستوى** مربوط بالمنهج، مش فورم حر.
4. **الواجب والتسليم** ظاهر للولي.
5. **ليد → تجربة → تحويل** مربوط بـ `PUBLIC_LEAD_ENDPOINT` ثم سجل الأسرة.
6. **دفع حقيقي** على نفس `recordPayment`.
7. **غرفة الحصة** بعد ما الحضور يبقى عادة.
8. **ثم فقط:** `PUBLIC_PORTAL_URL` و301 لـ `/login/`.

### 8. قرارات تحتاج المالك قبل الكود (لا تخمين)

1. من يعتمد نقلة المستوى: المعلم أم رئيس القسم أم الأدمن؟
2. هل ولي الأمر يرى ملاحظات المقيِّم الداخلية أم الملخص المنشور فقط؟
3. من أي عمر يدخل الطالب بنفسه؟
4. هل التشغيل يرى المالية أم نفصل دور finance؟
5. مزوّد الاجتماع، ومزوّد الدفع، ومزوّد واتساب.
6. منهج كل مسار: أسماء المستويات وعتبة الإتقان.

## English

Keep two deployables: the Astro marketing site, and one authenticated operations API. Do not buy another LMS. Grow `portal/` into three web consoles (owner, teacher, family) on that API. Academic progress, attendance and payment stay three different state machines. JSON is a rehearsal store; production is a database with the same domain rules. Do not point public login at this app until the teacher’s day (attendance → report) runs without demo passwords.

**Shipped 2026-10-17:** Teacher Day on the existing portal — `/app/today` and `GET /api/teacher/day`. Attendance, then complete, then a required report. Homework text on the report appends a `homeworkAssignments` row tied to that student and session. The roster is current assignments only (ended history stays on the student file). No new video room and no payments.

**Shipped 2026-10-17 (family hub):** `/app/home` and `GET /api/progress`. One card per child: next lesson, last lesson/report, homework, remaining credits. Fatima does not see Adam. A student sees only themselves. Invoices stay off this screen.
